# Production netstack engine: build, integration & validation evidence

This documents the state of the production gVisor netstack engine against the
four acceptance items, and is scrupulously honest about **what ran where**.

## Environment disclosure (read first)

The build/validation environment is a **headless Linux container with no attached
Android device, no `/dev/kvm`, and no CPU virtualization** (verified). A physical
device or a hardware‑accelerated emulator is therefore **impossible here**, so
genuine "real apps on a physical phone" throughput evidence could not be produced
in this environment. **No device logs, screenshots, or throughput numbers have
been fabricated.** Everything below either ran for real (and is labeled with where)
or is provided as a turnkey kit for you/CI to run on real hardware.

- **AAR:** `app/libs/netstack.aar` — package `dev.netvalve.bridge`, native

- **Integrated APK:** `prebuilt/app-netstack-arm64-debug.apk` (66 MB, includes the
  Go engine `libgojni.so`) — install this on an arm64 phone for the item‑4 tests.

Reproduce:

```bash
cd netstack && ./build-aar.sh                          # -> app/libs/netstack.aar (arm64)

```

### Why the sagernet fork (real gVisor integration finding)
Upstream `gvisor.dev/gvisor` **cannot** be built with plain `go build`/gomobile:
its intrusive lists/refcounts/marshal code is generated by its Bazel build and not
committed (errors: `undefined: ViewList`, `chunkRefs`, `waiterList`, …), and
`pkg/sync` ships un‑processed `.tmpl.s` template assembly plus a mislabeled
external test package on current master. The `sagernet/gvisor` fork commits the
generated files and is designed for exactly this (gomobile). Two small,
version‑driven adapter fixes were required and made:
1. `udp.NewForwarder` handler now returns `(handled bool)` (fork API).
2. `TCPConn.read` returns `long` and signals EOF via a thrown exception (gomobile
   mapping of Go `(int, error)`); the Kotlin adapter converts to `Int`/`-1`.

## Host validation (ran for real, this env)

`ThrottleForwardingIntegration` wires the **real** `FlowSupervisor` +
`ConnectionManager` + `ThrottleManager` + `TokenBucket` + `RuleEngine` +
`StatsCollector` and relays bytes over **real `java.net` TCP/UDP loopback
sockets** (real threads, real wall‑clock). The only parts not exercised are the
gVisor Go packet parser and Android `VpnService` — both replaced by the exact
byte‑stream contract netstack provides.

```

TCP DOWNLOAD 2 MB/s cap  : 8 MB in 3.751 s  -> 2.13 MB/s     [reduced≠blocked, 0 loss]
TCP DOWNLOAD 8 Mbps cap  : 4 MB in 3.945 s  -> 1.01 MB/s     [reduced≠blocked, 0 loss]

UDP ECHO     2 MB/s cap  : 200/200 datagrams echoed          [round-trip, no loss/deadlock]
=> 12 passed, 0 failed
```
The same logic ships as an **on‑device** instrumentation test
(`ThrottleForwardingInstrumentedTest`) so you can reproduce it in the Android
runtime.

## Runtime fix (2026-07-24): "works, then stops after a few seconds"

**Root cause — relay thread‑pool starvation.** Each flow runs two coroutines that
**block** on reads (netstack gonet + upstream socket). They ran on `Dispatchers.IO`,
which caps at **64** threads. A real page opens dozens of concurrent (often
keep‑alive) connections; once ~31 flows are up, their ~62 blocked threads exhaust
the pool, so `pace()` delays can't resume and new reads never get a thread — the
tunnel forwards for a few seconds, then stalls. It is not the throttle logic and
not the Go engine.

**Fix.** The relay now runs on `Dispatchers.IO.limitedParallelism(512)` (a
dedicated, larger blocking pool that doesn't starve the shared IO pool used by
Room/DataStore). Reproduced + verified on real sockets:
```
CONCURRENCY: 120 keep-alive flows (each = 2 blocking relay coroutines)
  parallelism=64  (old cap): served  31/120 flows   <- the stall, reproduced
  parallelism=512 (the fix): served 120/120 flows   <- fixed
```
(True 300+‑connection scale at low RAM ultimately wants NIO upstreams; 512 blocking
slots is the pragmatic correctness fix — see docs/LIMITATIONS.md.)

**Also added, for diagnosis + resilience (netstack engine):**
- Go‑side **panic recovery** in both TCP/UDP forwarder callbacks (a single bad flow
  can no longer crash the whole Go runtime), with the panic logged.
- The Go `Log` callback is now **wired to the app Logger** (was a no‑op), so
  netstack messages appear on the Logs screen + logcat.
- A **liveness beacon**: every 5 s the engine logs
  `[netstack] netstack alive: tcpFlows=… udpFlows=…`. This is the definitive
  triage signal — if it keeps printing while traffic is dead, the stall is on the
  Kotlin/relay side; if it stops, the Go runtime died.
